# Docker и ibcmd

> <img src="../resources/brand/cat-focus.png" alt="" width="26" align="left"> Команды идут в контейнер, а Предприятие и Конфигуратор с окном открываются на этой машине, если на ней есть платформа.

Команды vrunner могут выполняться не на локальной машине, а внутри Docker-контейнера с платформой 1С. Это полезно, когда платформа не установлена или её негде устанавливать:

- единое окружение у всей команды — версия платформы зашита в образ;
- работа в **GitHub Codespaces** и dev-контейнерах: в облачной среде нет GUI и установленной платформы, но серверные операции (создание ИБ, загрузка/выгрузка конфигурации, сборка) выполняются в контейнере прямо из расширения;
- тот же образ используется в CI — локальный запуск и пайплайн ведут себя одинаково.

## Включение

```json
{
  "1c-platform-tools.docker.enabled": true,
  "1c-platform-tools.docker.image": "your-registry/vrunner:8.3.27"
}
```

## Что доступно в контейнере

- Рабочая папка проекта монтируется в контейнер, пути к файловой ИБ и исходникам подставляются сами. Файл или база вне папки проекта контейнеру не видны: такая команда не запускается.
- Команды через `ibcmd` работают в любом образе с компонентом сервера, `ibcmd` включается в [профиле запуска](launch-profiles.md). Без него vrunner запускает пакетный конфигуратор: он, как и тесты в Предприятии, работает, если образ запускает клиент через xvfb.
- **Запустить Предприятие** и **Запустить Конфигуратор** выполняются на этой машине, если на ней установлена платформа; тогда им нужен и локальный OneScript. Без платформы они запускаются в отдельном контейнере, и окно видно, если образ умеет показывать графику. Команда завершается, как только клиент запущен, а его вывод показывает задача с тем же названием: остановка задачи закрывает клиент.
- `--no-wait` в контейнер не передаётся, в том числе из секции `yaxunit` профиля: контейнер завершается вместе с vrunner.
- Остальным командам локальный OneScript не нужен, кроме установки зависимостей и задач OneScript.
- Образ должен содержать платформу 1С:Предприятие с компонентом сервера (для `ibcmd`) и vanessa-runner.

## Параметры docker run

Сеть, тома с лицензиями и другие параметры `docker run` задаются в `docker.runArgs`, каждый отдельным элементом:

```json
{
  "1c-platform-tools.docker.runArgs": ["--network", "host", "-v", "/opt/1c/licenses:/var/1C/licenses:ro"]
}
```

Порты (`-p`, `--publish`) публикуются только Предприятию и Конфигуратору, открытым в контейнере.

С podman на системах с SELinux добавьте `"--security-opt", "label=disable"`, иначе контейнер не получит доступа к папке проекта.

## Где взять образ

Готовые публичные образы с платформой 1С не распространяются — лицензия 1С не позволяет. Образ собирается самостоятельно:

- **[pravets/onec-images](https://github.com/pravets/onec-images)** — рецепты и готовые GitHub Actions для сборки образов платформы и **vrunner** в свой registry; для скачивания дистрибутивов нужны учётные данные [releases.1c.ru](https://releases.1c.ru).
- **[firstBitMarksistskaya/onec-docker](https://github.com/firstBitMarksistskaya/onec-docker)** — альтернативный набор, включает образы для Jenkins, k8s и gitsync.

Для расширения нужен образ с vanessa-runner (в onec-images — образ `vrunner`).

## GitHub Codespaces

Способа два: платформа прямо в контейнере Codespace или Docker внутри Codespace.

### Платформа в самом контейнере

Платформа 1С и OneScript ставятся в образ разработки, Docker-режим не нужен и остаётся выключенным. Работают пакетные команды: сборка и разбор `cf`/`cfe`/`epf`, загрузка и выгрузка исходников, обслуживание ИБ. Для них нужен `ibcmd`, то есть компонент сервера в образе; он включается параметрами профиля запуска vanessa-runner.

<img src="../resources/brand/bird-warn.png" alt="" width="28" align="left"> Графической оболочки в контейнере нет, поэтому клиент и конфигуратор не запустятся: команды из дерева не убраны, но перед запуском предупреждают об этом.

Адреса локальных сервисов расширение пробрасывает наружу само: и корень публикации автономного сервера, и отчёт Allure открываются в браузере на вашей машине.

### Docker внутри Codespace

1. В `devcontainer.json` подключите Docker: feature `docker-in-docker` или `docker-outside-of-docker`. Во втором случае демон видит пути хоста, поэтому передайте путь рабочей папки на хосте: `"remoteEnv": { "LOCAL_WORKSPACE_FOLDER": "${localWorkspaceFolder}" }`.
2. Авторизуйтесь в своём registry (`docker login`) и укажите образ в `1c-platform-tools.docker.image`.
3. Включите `1c-platform-tools.docker.enabled` — команды дерева **1С: Инструменты** будут выполняться в контейнере внутри Codespace.

### Загрузка компонентов

В Codespaces вы уже авторизованы в GitHub, поэтому расширение берёт эту сессию и лимит анонимных запросов не мешает загрузке компонентов. См. [Токен GitHub](components.md#токен-github).
